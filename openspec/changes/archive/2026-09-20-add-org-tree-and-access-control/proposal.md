## Why

当前系统没有用户、组织与授权：`tenant_id` 取自可伪造的 `X-Tenant-ID`，会话与审计写死 `local-user`。未落地的 `add-auth-and-rbac` / `add-corpus-access-scope` 按「一人一主部门 + spec/fault 可见性」设计，对不上奥特莱物物流科技有限公司的真实结构：部门树、一人多岗、编制与岗位分离、密级单独审批、项目按专业切片。身份地基必须按这套规则重建，否则权限 demo 与后续检索过滤都会建在错误模型上。

## What Changes

- 新增 `identity-access`：会话登录、组织树、岗位、角色、权限、编制、密级、项目授权，以及受保护接口的动作校验与真实用户归属。
- 新增 `corpus-access`：文档携带组织节点、可选项目、专业、密级；列表与检索按内置可见性规则过滤。
- **取代** 尚未实现的 `add-auth-and-rbac` 与 `add-corpus-access-scope`（一人一主部门、`kind=spec|fault|general` 当权限开关、文档级 ACL）。那两份 change 不得按原文实施。
- **BREAKING**：受保护接口需要登录；租户只来自登录用户，忽略 `X-Tenant-ID`。
- 认证：用户名 + 密码（argon2id），HttpOnly Cookie 服务端会话；登录限流与失败锁定；无内置默认口令。
- 授权：权限只挂角色；人只绑岗位；岗位再关联角色。数据范围不进权限串。
- 组织：一棵组织树（本级视野、不含下级）；岗位必挂一个组织节点；一人可多岗；编制边用于「有家园无该部岗位」；地点（太原/朔州/苏州）挂在人上，不是树的一层。
- 密级：账号初始为一般；绑岗/换岗/加岗/减岗时表单必选一般或核心，系统不猜、不做岗位默认 max。
- 项目授权：把人授进项目（不过密级，仍按岗位专业并集切一刀）；空专业岗不贡献项目切片；不做文档级授权。
- 专业枚举：软件、电气、机械、采购、运营、财务、销售。
- 前端：登录、鉴权、岗位/组织/项目授权管理（管理员）、按权限显示功能；种子数据覆盖袁工/马工可见性矩阵。
- 非目标：企业微信 SSO、Casbin/OPA、chunk 级 ACL、管理员默认可看全库、把分公司拆成多个租户、汇报线自动看下级。

## Capabilities

### New Capabilities
- `identity-access`: 账号与会话、组织树与地点、岗位（挂部门）与多岗、角色与动作权限、编制、密级表单、项目授权、Principal 与受保护操作校验。
- `corpus-access`: 语料的组织节点/项目/专业/密级标签，以及基于 Principal 的列表与检索可见性。

### Modified Capabilities
- `knowledge-qa`: 问答检索 MUST 只命中当前用户可见语料，不得引用不可见文档。
- `document-ingestion`: 上传与版本 MUST 持久化组织、项目、专业、密级标签，并继承到可检索切片。

## Impact

- 数据：组织树、用户、岗位、角色、权限、编制、会话、项目成员等表；文档/版本/Milvus chunk 增加组织、项目、专业、密级；Alembic 迁移与奥特莱物种子组织。
- 代码：安全模块、Principal、`require_permission`、可见性谓词接入文档列表与 `SearchService`；`tenant_dependency` 改为登录用户。
- 接口：登录/登出/当前用户、组织与岗位管理、用户绑岗（含密级必选）、项目授权；既有接口未登录 401。
- 前端：登录页、管理页、Cookie 凭据、401/403。
- 测试：袁工/马工可见性矩阵、换岗必填密级、项目专业切片、伪造租户头无效。
- 依赖：argon2。未实现的两份旧 change 在 README 中标明由本 change 取代。
