## Why

会话记忆目前只有"最近 N 轮"的滑动窗口，没有长期记忆：跨天或多轮长对话后，早期信息会从窗口滑出并彻底丢失上下文。同时，压缩机制尚未建立，原文缺少"已压缩"标记，无法在保留审计能力的前提下把旧消息移出窗口。需要短期滑动窗口与长期记忆压缩结合，并保证全量原文永久保留在数据库；用户也应能在聊天主界面看到当前会话记忆摘要。

## What Changes

- **短期记忆**：保持滑动窗口（最近 N 轮未压缩消息，`KB_HISTORY_TURNS`）。
- **长期记忆**：按**未压缩窗口**的 token 预算（`KB_MEMORY_TOKEN_BUDGET`，定义 A）触发压缩；滚动摘要另有硬顶（`KB_SUMMARY_TOKEN_CAP`）。占位约 6k–8k / 600–800，env 可调，正式默认值验收前校准。
- **异步压缩**：聊天 SSE 不阻塞；超预算时仅入队，由后台 worker 加锁生成摘要并标记已压缩消息。
- **原文不删除**：被压缩的消息只标记 `compressed=true` 并移出窗口，原文永久保留在数据库，供审计与回溯。
- **三层拼接**：加载时使用"长期记忆摘要 + 未压缩的最近消息 + 当前问题"构造上下文；查询改写同样使用该上下文。
- **主界面可见**：聊天页只读展示最新「会话记忆」摘要（如侧栏卡片）；无摘要时空态/隐藏；用户不可编辑或清空。
- **自观测**：L1 压缩健康度事件（budget_check / enqueued / done / failed）；L2 golden 探针断言压缩后关键实体仍可追问命中；人调 env，不自调节预算。
- **持久化位置**：会话与消息、记忆摘要、LangGraph checkpoint 全部落 PostgreSQL；Redis 仅用于缓存、限流与压缩队列，不保存对话事实来源。
- **会话标识**：前端必须稳定传递 `session_id`（等同 `conversation_id`），跨页面、跨天、清缓存后仍能恢复同一会话。
- 非目标：层级摘要（摘要的摘要）、跨会话/跨用户记忆、向量化记忆检索、用户编辑/清空摘要、默认同步压缩、以「摘要+窗口」合计作为压缩触发预算、根据观测自动改预算、默认 LLM-as-judge 评摘要。

## Capabilities

### New Capabilities
- 无。

### Modified Capabilities
- `multi-turn-chat`: 会话记忆由单一滑动窗口改为"滑动窗口 + token 预算异步压缩的长期摘要"；明确原文保留、会话标识稳定性、主界面只读展示会话记忆，以及压缩自观测（L1 事件 + L2 探针）。

## Impact

- 数据：`messages` 增加 `compressed`、`token_count`、`summary_id`；新增 `conversation_summaries` 表与迁移。
- 服务：聊天路径按未压缩窗口超 `KB_MEMORY_TOKEN_BUDGET` 入队；压缩 worker 写摘要（受 `KB_SUMMARY_TOKEN_CAP`）并打标；会话加载改为三层拼接；只读接口返回最新摘要供 UI；发出 L1 `memory.*` 观测事件。
- 配置：上述预算/硬顶先占位实现，正式默认值验收前用 L1 信号 + L2 探针 + 真实长会话校准后写入。
- 问答链路：改写与生成节点使用摘要 + 窗口；checkpoint 仍落 PostgreSQL。
- 前端：会话标识持久化（URL + localStorage）并显式传递；聊天主界面只读「会话记忆」卡片；恢复失败时给出明确提示。
- 测试：跨天恢复自动化验收；主界面可见性验收；L2 golden 探针（压缩后实体仍可命中）；L1 事件字段可解析。
